# P1.1–P1.2 — Canonical DNA Model and Boundary Proposal

**Status:** Proposed for review  
**Phase:** P1 — Canonical Domain Model / Module Boundaries  
**Confirmed source:** the earlier GENis-system design conversation  
**Technical baseline:** `22178fe12d2084b9c8e1fd1cf897383bc67b3b0a`

This document separates restored decisions from new design proposals. A row marked **Confirmed** was
recoverable from the agreed plan. A row marked **Proposed** is an engineering recommendation and must
not be represented as an earlier user decision.

## 1. Confirmed decisions

- Offline operation inside a private LAN.
- One installation; not SaaS and not multi-tenant.
- FullStackHero modular monolith.
- PostgreSQL is the system of record.
- Local MinIO/files for object storage.
- Scientific engines are accessed through adapters.
- Canonical spine:
  `Case → EvidenceItem → BiologicalSample → GeneticProfile → Loci / Alleles / Peaks`.
- Agreed boundaries:
  Cases, Evidence, Samples, Genetics/Profiles, STR Kits, Frequency Tables, Matching,
  Interpretation, Kinship, MPI/MissingPersons, DVI, ScientificAnalysis/AnalysisRun,
  Reporting, Audit, Identity/Admin.

### Identity rules — proposed

1. Every aggregate receives an immutable internal identifier generated by the installation.
2. External case, evidence, laboratory, instrument, and import identifiers are stored separately and
   never replace the internal identifier.
3. Human-readable numbers are not database keys.
4. No forensic entity contains `TenantId`.
5. Imported records retain source-system identity and import-batch provenance.
6. A scientific result is never silently overwritten; a correction creates a new version that
   supersedes the prior version.
7. Timestamps use UTC internally while reports may render the configured local timezone.
8. Identity allocation must remain available without internet or a central external service.

### Canonical relationship rules — proposed

- A `Case` references zero or more `EvidenceItem` records through contracts.
- An `EvidenceItem` can yield one or more `BiologicalSample` records.
- A derived sample records its immediate parent sample so derivation remains traceable.
- A `BiologicalSample` can participate in multiple `AnalysisRun` records.
- A completed analysis may produce a candidate profile version; approval determines whether it
  becomes eligible for matching or reporting.
- A `GeneticProfile` version owns its locus, allele-call, and peak observations as one immutable
  scientific snapshot.
- STR-kit and frequency-table versions referenced by an approved result cannot be mutated.

Cardinalities above are proposals because the earlier conversation did not expose a complete
relationship table.

## 3. P1.2 ownership proposal

Each business record has one authoritative owner. Other modules use its contracts or immutable
identifier and may not update its tables.

| Module boundary | Proposed authoritative ownership |
|---|---|
| Cases | Case identity, classification, references, and case lifecycle |
| Evidence | EvidenceItem identity and append-only custody history |
| Samples | BiologicalSample identity, collection metadata, and derivation lineage |
| Genetics/Profiles | GeneticProfile versions, loci, allele calls, peaks, validation state |
| STR Kits | Versioned STR-kit, panel, marker, allele-range, and analytical definitions |
| Frequency Tables | Versioned population datasets and allele-frequency entries |
| ScientificAnalysis/AnalysisRun | AnalysisRun inputs, adapter/version metadata, parameters, outputs, logs, reproducibility hash |
| Matching | Search request, candidate set, review decision, and disposition |
| Interpretation | Interpretation inputs, hypotheses, conclusions, review, and approval |
| Kinship | Pedigree/relationship hypotheses, calculation runs, statistics, review, and approval |
| MPI/MissingPersons | Missing-person records and the identification workflow it coordinates |
| DVI | Disaster incident, victim record, and DVI identification workflow |
| Reporting | Immutable report snapshot, issue/supersession history, and disclosure package |
| Audit | Technical/security audit trail; it does not own forensic business state |
| Identity/Admin | Users, roles, permissions, local administration; it does not own forensic records |

### Proposed dependency direction

Dependencies refer to contracts only; runtime-project references remain forbidden.

```text
Cases
  <- Evidence
    <- Samples
      <- ScientificAnalysis
      <- Genetics/Profiles

STR Kits ---------> ScientificAnalysis
STR Kits ---------> Genetics/Profiles
Frequency Tables -> Matching
Frequency Tables -> Interpretation
Frequency Tables -> Kinship
Genetics/Profiles -> Matching
Genetics/Profiles -> Interpretation
Genetics/Profiles -> Kinship
Matching ---------> Interpretation

MPI and DVI coordinate approved contracts from Cases, Evidence, Samples,
Genetics/Profiles, Matching, Interpretation, Kinship, and Reporting.
```

The apparent analysis/profile feedback loop must not become a project-reference cycle:

- `ScientificAnalysis` publishes an immutable analysis-output contract.
- `Genetics/Profiles` consumes that output and owns the approved profile.
- A later analysis may consume a profile snapshot through a neutral input contract or orchestration
  request; it must not reference the Profiles runtime project.

## 4. Boundary invariants — proposed

- A module never writes another module's tables.
- A module references another module only through its Contracts assembly.
- Cross-module identifiers are opaque; consumers do not infer meaning from identifier formats.
- Evidence custody, scientific output, approvals, and reports use append-only history or explicit
  supersession; no destructive history rewrite.
- Matching never mutates a source profile.
- Reporting never becomes the source of the facts it renders.
- Audit records actions but cannot substitute for the domain's own custody or scientific history.
- MPI and DVI orchestrate workflows; they do not duplicate authoritative DNA observations.
- Scientific adapters cannot access application tables directly.
- Every adapter invocation records engine name, engine version, input hash, parameters, output hash,
  start/end time, outcome, and initiating identity.
- No module requires internet connectivity for its core workflow.
